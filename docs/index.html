TamaClaudchi

A dashboard for watching several Claude Code agents at once. One Python file, plain HTML/CSS/JS, stdlib only, no build step, no dependencies, no external assets. This is the developer guide; see the README to run it.

Shape

server.py       aggregation + HTTP (stdlib http.server)
web/index.html  the page
web/app.js      all rendering and interaction
web/style.css   one token set, light + dark
hooks/          optional Claude Code hook script

The frontend polls /api/state every 600 ms; the server caches a built board for 250 ms. Those two numbers are the lag between an agent changing state and the card saying so, so keep the cache below the poll.

Where the data comes from

sourcegives
~/.claude/sessions/<pid>.jsonregistry: pid, sessionId, cwd, status
tmux list-panes + pswhich pane each agent pid lives in
~/.claude/projects/<slug>/<sid>.jsonltranscript: chat, model, tokens, title, MCP tools
~/.claude/tasks/<sid>/*.jsontask list and dependency edges
~/.claude/agent-events/<sid>.jsonlhook events (optional)
~/.claude.jsonMCP servers configured per directory
tmux capture-panelive truth: spinner, permission mode, dialogs, sub-agent roster

Written state, all user-owned and written atomically: agent-manager-names.json (renames), agent-manager-artifacts.json (pinned files), agent-manager-spawns.json (who launched whom).

Endpoints

All gated on the token — no exceptions.

GET
/api/statethe board; polled
/api/chatone conversation, live or past
/api/historypast sessions; own 30 s TTL, never in the poll
/api/artifacts, /api/browsepinned files; path completion (dirs=1 folders only, base= resolves a relative prefix against the agent's folder). Listing only — it returns names, never contents.
/api/sessions, /api/debugresumable sessions; why a session isn't on the board
POST
/api/send, /api/keytype into a pane; press one allowed key
/api/model, /api/modeswitch model; cycle permission mode
/api/spawn, /api/kill, /api/renamelifecycle
/api/artifact-pinwatch a file or folder

Security model

One shared token gates every /api/* request. That single mechanism defeats CSRF, DNS-rebinding and shared-host snooping, chosen over layering Origin checks + CORS + content-type sniffing. It rides in the URL fragment (never sent on the wire) and comes back as X-Auth-Token.

Non-negotiable when changing this code.
  • Anything reaching tmux takes an allowlist, never free text: ALLOWED_KEYS, CYCLE_MODES, _MODEL_ID_RE, the --resume pattern, artifact extensions. Validate before the pane lookup.
  • read_artifact and /api/chat resolve paths only from a list the session itself produced — a whitelist by construction, not a prefix check.
  • Every subprocess call is list-form. No shell=True, no eval, ever.
  • Static files come only from WEB_DIR + os.sep (the trailing separator matters).
  • No outbound network calls, no external assets. Keep it airgap-clean.
  • MCP config is never echoed: env, args and URLs carry API keys, so only a server's name and status are returned.

Standing battery, before every push: unauthenticated request to every endpoint → 401; path traversal raw and URL-encoded → 404; injection into model / mode / key / resume / target → 400; malformed, oversized and non-object bodies → 400.

Testing

python3 scratch/server-test.py   # pure functions, no tmux, no network
node    scratch/render-test.js   # app.js in a vm with a DOM stub

Both are plain scripts with no framework. The render harness runs app.js in a vm context; note that top-level const/let are not on the vm global, so assign them by running code inside the same context.

There is no headless browser here. Verify sprites by dumping them as ASCII grids and colours by computing contrast ratios — both are done throughout the tests. Never claim a visual change works without looking at something.

The mascot

Every axis encodes something real. Sprites are pixel maps in app.js on an 18×16 grid.

body colourgit repo (or the folder, outside a repo) — worktrees of one repo share it
hatthe model: wizard / crown / poet / kitsune = Fable / Opus / Sonnet / Haiku
held itemgit branch; main always gets the sword
eggno reply yet, so the model is unknown

Hats occupy rows 0–3 (a few reach lower); every item is held at x15–18, so the axes cannot collide — two items used to be drawn off-hand at x0–2, which is where the kitsune mask sits. Eyes are drawn before hats so a hat can cover them. Items get an automatic rim (haloOf) in the pet's own outline colour: it keeps a pale item readable on a pale card, and a hard black rim there was the only such edge on the sprite. Items are drawn in the lower-case pastel roles of CLR, hats in the saturated upper-case ones. The viewBox is inset by one cell on each side so those rims are not clipped. Colours and items are assigned, not hashed: the hash picks a preferred slot and collisions probe forward, because 8 keys in 8 slots collide 99.8% of the time.

Hard-won knowledge

  • User turns are not always strings. Some are [{"type":"text"}] lists. Both parsers handle that; tool results stay excluded.
  • Dialogs must be read from the pane, not from hooks. Detection accepts a ❯ cursor, an "Esc to cancel" line, or a yes-ish option — requiring "yes" made every AskUserQuestion menu invisible.
  • A digit does not mean the same thing in every dialog. A permission prompt takes it as the answer; an AskUserQuestion menu may only move its selection cursor, so answering one did nothing until send_key followed up with Enter. Two menus with identical footer hints behave differently, so needs_confirm watches what the pane did — same question still up, cursor parked on that option — rather than trying to classify the dialog.
  • Option rows carry the preview panel. A menu with previews draws the box to the right of each option on the same line, so labels have to be cut at the box-drawing block.
  • The mode footer is not the last line. Trailing rows ("/clear to save 488k tokens", the sub-agent roster) sit below it, so scan the last few lines upward.
  • The composer is not the last line either — it is the bottom-most ❯ line. Past user turns use the same marker.
  • The context window cannot be read off the model name. Two sessions both reporting claude-opus-5 were observed with peak prompts of 170k and 822k, and nothing on the machine declares which window either is on — not the transcript (no beta field), not ~/.claude/sessions/<pid>.json, not ~/.claude.json. The only evidence is behavioural, so _ctx_peak tracks the largest prompt each session has been seen holding: a prompt past 200k could not have fit a 200k window. It must be the peak, not the current size — inferring from the current one would halve the window right after a compaction and make the percentage jump upward. Percentages are therefore not comparable between sessions, and anything showing one must show its denominator.
  • Transcript mtime is not activity. Claude Code rewrites untimestamped bookkeeping records; sort on the newest timestamped record instead.
  • A Task sub-agent's tool_use is only written once it finishes. Live ones come from the pane's agent roster (● main / ◯ type).
  • tmux starting is not Claude starting. If a --resume can't be honoured, Claude Code prints "No conversation found with session ID" and exits at once, leaving a new tmux session at a shell prompt and nothing on the board — while the spawn reported success. spawn_session now waits for the UI to come up or for that message, and tears the empty session down. Match the message exactly: a looser rule ("command not found") also matched the noise a login profile prints into every new pane, and would have killed good sessions.
  • Resuming a conversation that is already open starts a second process on the same session id and transcript. Both appear on the board under one id, they interleave their writes, and a kill that finds an agent by id alone can hit the wrong one. Resume is refused for a live session, and kill takes a pid to disambiguate.
  • claude --resume keeps the same session id and the same transcript. A resurrected agent is the session its headstone was cut for, so "live" and "past" can name the same id. /api/history re-checks its cached rows against the live board, and the cemetery re-checks again on every render — the cache alone left a running agent with a grave for up to 90 seconds.
  • A session's id can change while you are looking at it. A process with no registry entry yet is shown under a new-<pid> placeholder, and a resumed session spends about half a second there because its transcript is older than its process. The pid is the stable identity: it pins the id server-side so it cannot flap back, and the open card follows the pid rather than closing itself.
  • A click's target is the nearest common ancestor of press and release. Selecting text in the conversation and releasing outside the window therefore reports the modal backdrop, and closed the card mid-selection. Close on a backdrop click only when the press began on the backdrop.
  • Walk up the process tree, not down. Mapping panes to agents by expanding every pane's descendants needs the whole process table, and ps -eo pid=,ppid= was 50 ms of a 67 ms board build on a machine with 2,500 processes — a 2,500-entry tree to answer a question about a dozen. Enumerate the Claude processes and walk up to their pane instead. Check the uid before reading comm: one stat against an open-read-close, and on a shared login box only 5% of processes were ours. Together: 67 ms → 22 ms and one fewer subprocess.
  • tmux daemonises, so a spawned session's process parent is the tmux server. Lineage must be recorded while both sessions are alive — the link comes from the parent's transcript (_NEW_SESSION_RE), matched by tmux session name, so reusing one name for several agents in turn only ever links whichever was alive at the time. Only a real agent is a parent: sessions started from the dashboard were once attributed to "dashboard", which is not one, and which — being keyed by session name — stuck to whatever unrelated agent later took the name. In the cemetery a headstone can only share a plot with a launcher that is also dead; otherwise it just names the launcher on the card.
  • A transcript record can be larger than any fixed head window (one starts with a 205 KB line). Read by lines, not bytes.
  • /proc/<pid> mtime is not process start time. Use field 22 of /proc/<pid>/stat plus uptime.
  • >> is a signed shift in JS. Hashes past 2³¹ go negative and index arrays with -3. Use >>>.
  • FNV-1a's lowest bit is only the parity of the input characters. Its multiplier is odd, so lowbit(h·prime) = lowbit(h): deriving one bit per cell with hash(seed + x + y) & 1 made the user identicon the same checkerboard for every name. Seed a xorshift and take whole words from it. Identicons also need a fixed cell count — rolling each cell independently leaves some names with three lit pixels, which reads as scattered dots.
  • input[type=number].selectionStart is null, so restoring a caret sends it to 0 and reverses typing. Do not rebuild a focused control at all.
  • Same-specificity CSS is decided by file order. .mascot silently overrode .legend-pet for weeks. Use .mascot.legend-pet.
  • Agents on another host are invisible to /proc and tmux. A session inside srun shares ~/.claude only; it is surfaced read-only.
  • Compaction shows no elapsed timer for its first ~15 seconds — just ✶ Compacting conversation…. Keying the spinner off the timer therefore reported nothing for most of a compaction pass. The animated glyph at the line start is present from second zero, and the trailing … is what separates a live spinner from a finished ✻ Crunched for 5s.
  • /model opens its own "Switch model?" dialog, so the model has not changed when set_model returns. It is surfaced on the card rather than auto-confirmed: the dialog warns that the conversation is cached per model and the whole history gets re-read.
  • A working agent often has no spinner. Claude Code drops the spinner line the moment prose starts streaming, leaving only "esc to interrupt" in the footer — and nothing reaches the transcript until the turn ends. Compaction is the mirror case: its spinner reads Compacting conversation… (18s) with a ▰▱ 19% bar, so the phrase regex must allow several words.
  • A click needs mousedown and mouseup on the same element. Any innerHTML rebuild landing between the two throws the click away, which is what made buttons need pressing twice. Nothing re-renders while a pointer is held, and transient UI state (an armed Kill button) lives in JS, never on the element.

Rendering rules

The poll rebuilds the board constantly, and replacing innerHTML destroys every piece of DOM state inside it — scroll positions, open <details>, text selection, the caret. So:

  • compare the markup first and skip the write entirely when nothing changed (lastBodyHtml), and compare it per element for anything repeated — one string for a whole list is always different, so the guard never fires (lastGridParts);
  • never rebuild a container while it holds the focus or a live selection;
  • update results in place rather than re-rendering controls the user is typing into;
  • keep exactly one scroll container per view — a scrollable box nested in a scrollable panel traps the wheel and loses its position;
  • hold transient UI state (an armed Kill button) in JS, never on the element, or the next rebuild wipes it;
  • cache a completion request by the directory it lists, not by the whole string — the browser filters within one directory itself, so typing a 49-character path costs 9 requests instead of 49, and a long filename costs none;
  • never repeat a sprite per row. A pet is ~200 <rect>s — fine once on a card, ruinous beside every message. A 150-message Exchange reached 7,773 rects and 625 KB of markup that the browser re-parsed on every render. Define it once as a <symbol> and <use> it: 249 rects, 170 KB;
  • gate a refetch on something that actually changes. The open conversation was re-fetched every poll; a busy agent's transcript always differs, so that was ~24 ms of server work re-reading a 4 MB tail plus ~60 KB on the wire, 100 times a minute, to render identical messages. last_activity is already on the board and only moves when a message lands, so it decides (chatIsStale);
  • position a popup from its trigger's rect (placeMenu: fixed, in <body>, flipped up when there is no room below, clamped to the viewport) — offsets relative to whatever container it lands in are tuned for one call site and silently wrong at the next.

Motion

The board is meant to be calm, and everything twitchy has been a bug report:

  • No steps() anywhere. A two-frame timeline is a hard jump with nothing in between — a bump by construction. The pets do not move at all; state is carried by the mood pill, the badge, the border and the context gauge.
  • Pausing an animation on hover is worse than the animation. It snaps the element from wherever the timeline had it back to zero, the instant the cursor arrives.
  • The worst motion bug had nothing to do with CSS. The shelf was written as one grid.innerHTML = everything, guarded by comparing the whole string — which, measured against a live board, differs on 100% of polls (one card's "5s ago" ticking over is enough). So every card element was destroyed and recreated 1.7 times a second. A card under the cursor was reborn with transform: none, matched :hover immediately, and slid 0 → -2px again, forever. It looked exactly like a broken keyframe, and no amount of editing keyframes touched it. paintGrid now writes one slot at a time, skips anything under the pointer, and defers a reshuffle while a card is hovered. Measure DOM writes before theorising about animation.
  • Sliding an element on :hover can also flicker. The shift moves it out from under a cursor near its trailing edge, hover drops, it slides back, and it oscillates. The fix is a negative-z-index ::before pad inset past the shift, sized under half the grid gap so neighbours never overlap.
  • Only pulse (a smooth opacity breathe), the one-shot fade-up, and the deliberate walking loader remain.

Working agreements

Minimalism, modularity, cleanliness, efficiency, safety. Prefer deleting to adding, keep data-driven tables over branching code, and run the dead-code sweep (unused JS/Python functions, unused CSS classes) plus the security battery before every push.
